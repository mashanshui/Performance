# 线程调度与原生工具

[返回导航](README.md)

## 定位与接入

这些工具用于线程调度和性能实验；内存指标已经通过独立 `MemoryReporter` 接入 SDK 的配置、关闭和上传生命周期。示例 `App` 会调用 `ThreadUtils.setMainThreadMaxPriority`；CPUFreeDemo 和 GcInhibitDemo 是独立类，没有主页面按钮直接调用。

## 线程池

| 实现 | 当前参数与行为 |
| --- | --- |
| `CPUThreadPoolExecutor` | 核心/最大线程数均为 availableProcessors，队列容量 512，DISPLAY 优先级 |
| `IOThreadPoolExecutor` | 核心 1、最大 64、空闲回收 10 秒，SynchronousQueue，LESS_FAVORABLE 优先级 |
| `CoreThreadFactory` | 生成前缀+序号线程名，在线程执行入口设置 Android 线程优先级 |
| `CoreThreadPoolExecutor` | 安装自定义拒绝处理器；当前 rejectedExecution 为空，会丢弃拒绝任务 |

参数体现 CPU 限并发、IO 允许更多并发的设计意图，但源码注释提到的“拒绝监控和兜底线程”尚未实现。构造函数也没有预启动全部核心线程，不能把注释中的“创建时预先创建”作为本项目行为。

入口示例：

~~~kotlin
// 仅用于理解独立工具的调用方式；调用方负责任务生命周期。
CPUThreadPoolExecutor.instance.execute { /* CPU 工作 */ }
IOThreadPoolExecutor.instance.execute { /* IO 工作 */ }
~~~

这些单例不由 SDK close 关闭，生产调用前应评估任务取消和拒绝可观测性。

## 优先级、CPU 与内存

`ThreadUtils.setMainThreadMaxPriority` 有 MainThread 注解，实际调用 Process.setThreadPriority 设置当前调用线程的 URGENT_AUDIO 优先级。渲染线程版本扫描 /proc 的线程 stat 查找 RenderThread，找不到返回 -1，调用处没有另行拦截。

`NativeLib.getCpuTime` 通过 times 读取本进程用户态和系统态 CPU 时间，并按时钟 tick 转换为秒；失败返回 -1。`CPUFreeHelper` 用 CPU 时间差除以墙上时间差和核数，低于 0.1 时按 HIGH/MIDDLE/LOW 顺序在主线程消费一个回调。

当前 CPUFreeHelper 在循环中没有推进初始基线，计算是相对 start 的累计平均；stop 后再次 start 不重置 mStop，重复 start 也没有幂等保护。它使用 GlobalScope，不能当作已完善生命周期的滚动 CPU 利用率采集器。

`MemoryUtils.getMemoryInfo` 仍是旧的诊断字符串入口；统一上报由 `MemorySampler` 和 `MemoryReporter` 完成。内存指标协议要求的三项原始值按以下口径获取：PSS 使用 `Debug.getPss() * 1024`，VSS 读取 `/proc/self/status` 的 `VmSize * 1024`，Java 堆使用 `Runtime.totalMemory() - Runtime.freeMemory()`。三项读取失败时各自保留缺失值，不能用 0 替代。

2026-09-09 在当前连接的 Pixel 4 XL（Android API 33，arm64-v8a）上执行了 [MemorySamplingTimingTest](../../app/src/androidTest/java/com/example/performance/MemorySamplingTimingTest.kt)。10 次预热后进行 120 次正式采样，同一轮交替比较两种 PSS 读取方式：`Debug.MemoryInfo.totalPss` 平均 21.172 ms、P95 21.922 ms，`Debug.getPss()` 平均 5.481 ms、P95 6.491 ms；VSS 平均 0.525 ms、P95 0.644 ms；Java 堆平均 0.006 ms、P95 0.007 ms；三项组合分别平均 21.668 ms 和 6.031 ms，P95 分别为 22.492 ms 和 7.216 ms。两种 PSS 数值可能因连续调用的时间差略有不同，但口径都是本进程 PSS。该结果只覆盖原始读取和解析，不包含事件对象、JSON、磁盘队列和网络上传，且不能外推到其他设备。

基于这次耗时，当前实现采用：PSS 使用 `Debug.getPss()`，采样任务放在 `memory-sampling` 工作线程，不在主线程或帧回调中读取；初始化、前台进入和后台确认时立即采样，前台每 60 秒一次，进程仍存活时后台每 5 分钟一次，回到前台后恢复 60 秒周期。后台切换延迟 700 ms 确认，以过滤旋转和页面切换空窗；Activity 场景只作为当前采样的可选字段。事件先原子写入独立队列，再由 `memory-upload` 线程批量发送。单次原始采集预算为 20 ms，当前设备 `Debug.getPss()` 组合 P95 为 7.216 ms。首版仅主进程采集，不跨进程求和。

## Kotlin 与 JNI 对应关系

| Kotlin 入口 | C++ 对应实现 | 当前机制 |
| --- | --- | --- |
| `NativeLib.stringFromJNI` | `nativelib.cpp` 同名 JNI 函数 | 返回测试字符串 |
| `NativeLib.getCpuTime` | `nativelib.cpp` | 进程 CPU 时间 |
| `bindMainThreadToMaxCore` | `nativelib.cpp` | 读取 cpuinfo_max_freq，选最高频率核，调用 sched_setaffinity(0, ...) |
| `bindCurrentThreadToMaxCore` | `nativelib.cpp` | 获取 gettid，再调用 sched_setaffinity |
| `openGcInhibit` | `hook_util.cpp` | hook libart ConcurrentGCTask::Run，代理中 sleep 后调用原函数 |
| `closeGcInhibit` | `hook_util.cpp` | 调用 shadowhook_unhook |

`bindMainThreadToMaxCore` 当前没有显式查找主线程 tid；应在主线程调用并实测亲和性，不能仅凭函数名推断跨线程调用效果。频率文件不可读或系统拒绝设置时返回 false。

`HookUtils.initHook` 初始化 ShadowHook UNIQUE 模式。GC Hook 的目标符号固定，依赖设备 libart；代理使用 sleep，实际按秒延迟，尽管 C++ 变量名使用 milliseconds。它是推迟这个 GC 任务的实验，不是关闭全部 GC。

原生构建由 [CMakeLists.txt](../../nativelib/src/main/cpp/CMakeLists.txt) 将两个 cpp 编入 nativelib，并链接 shadowhook、android、log。Gradle 限定 arm64-v8a；当多个依赖携带同名 ShadowHook so 时使用 `pickFirst` 保留一个实现，不能把 `libshadowhook.so` 排除，否则 Rhea 初始化会因 `UnsatisfiedLinkError` 失败。最终消费者仍需检查 APK 中的原生依赖是否齐全。
