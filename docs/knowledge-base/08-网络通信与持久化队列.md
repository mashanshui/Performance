# 网络通信与持久化队列

[返回导航](README.md)

## 公共网络层

`PerformanceConfig → NativeServiceConfig → NetworkConfig → NetworkClientFactory` 创建共享 OkHttp/Retrofit 和五个专用客户端。AppKeyInterceptor 添加 `X-App-Key`；网络日志可选，使用 BASIC 等级并设置敏感头脱敏，不记录请求正文。内存客户端固定向批次请求发送 `X-Schema-Version: 2`，内存泄漏报告客户端使用 multipart 请求。

`retryOnConnectionFailure(false)` 把重试决策留给持久化上传器。成功、HTTP 错误、网络错误、序列化错误和未知错误映射为 `NetworkResult`；协程取消重新抛出，不当成普通失败吞掉。错误体最多保留 8 KiB，日志应使用稳定 code/事件 ID 而非完整正文。

`Retry-After` 当前仅解析整数秒，不解析 HTTP 日期形式。重试仍受队列 nextAttemptAtMillis 控制，网络恢复或手动 flush 不会强制绕过它。

## 五种队列的差异

以下根目录均相对于应用 `noBackupFilesDir`。

| 项目 | Crash | Jank | FPS | 内存 | 内存泄漏报告 |
| --- | --- | --- | --- | --- | --- |
| 根目录 | performance-crash-reporter | performance-jank-reporter | performance-fps-reporter | performance-memory-reporter | performance-memory-leak-reporter |
| 保存内容 | 完整事件 JSON、重试状态 | ZIP 文件名和重试/待删除状态，ZIP 由 Rhea 保存 | current.json 聚合快照、封存事件、重试状态 | 完整 memory_sample JSON、重试状态 | metadata 与 report JSON、重试状态；不保存 HPROF |
| 入队触发 | app_start 或未处理异常 | 成功/部分导出后，以及启动对账 | 当前会话恢复或 SDK close 封存 | 初始化、前后台切换和周期采样 | KOOM report 回调 |
| 一轮上限 | 5 批 | 5 个 ZIP | 5 批 | 5 批 | 5 个 report |
| 周期/启动/网络恢复 | 支持 | 支持 | 支持，仅上传封存事件 | 支持 | 支持，入队后立即调度 |
| 容量 | 单批限制，正常队列无字节配额 | 原始 ZIP 配额传给 Rhea | 配额只覆盖 events | 20 MiB，包含 events 与 dead-letter | 20 MiB，包含 events 与 dead-letter；单个 report 2 MiB |
| 过期 | 7 天，转 dead-letter | TTL 由 Rhea 管理 | 配置 TTL，删除过期封存事件 | 配置 TTL，删除事件和 dead-letter | 7 天，删除过期事件 |
| 永久失败 | dead-letter | 标记待删除并删除原 ZIP | dead-letter | dead-letter；重试 10 次耗尽也隔离 | 400/401/403/409/413/415 或重试耗尽进入 dead-letter |
| 特有恢复状态 | 原子事件记录 | deletePending 与 pending ZIP 对账 | 上次 current.json 封存 | | HPROF 回调仅删除本地文件；accepted/duplicate 才删除 report 任务 |

Crash 的 dead-letter 有默认 100 文件限制；FPS 当前没有同样的 dead-letter 数量限制。内存和内存泄漏 report 的 dead-letter 与正常事件共用各自的 20 MiB 配额，超额时优先清理旧隔离文件。不要将某一队列的容量保证套用到另外四条链路。

内存队列每个样本生成一次 UUID eventId，原子写入后才进入上传选择；accepted/duplicate 才会删除事件。
网络中断、408、429、5xx 和 503 会保留原事件并按 Retry-After 或退避重试，上传器会校验 HTTP 200、requestId、
accepted/duplicate/rejected 总数及错误定位。

内存泄漏 report 在 KOOM 回调中生成一次 UUID eventId，先把 metadata 和 report 原子落盘到
`performance-memory-leak-reporter/events/<eventId>/`，再由后台线程请求
`POST ingest/v1/memory-reports`。请求只包含 `metadata`、`report` 两个 `application/json` part，
不创建 HPROF part；入队成功后删除 KOOM 原始 report JSON，HPROF 回调只删除本地 HPROF。HTTP 200
且响应 eventId 一致、status 为 `accepted` 或 `duplicate` 时才删除队列项；网络异常、超时和 503
按 `Retry-After`/指数退避保留原 eventId，其他明确永久错误进入 dead-letter。

## 成功判定与重试

| 分类 | Crash 当前实现 | Jank 当前实现 | FPS 当前实现 | 内存当前实现 | 内存泄漏 report 当前实现 |
| --- | --- | --- | --- | --- | --- |
| 有响应体的 2xx | 按 errors 定位处理；未校验 HTTP 必须 200 或响应总计数 | success=true 且 accepted/duplicate；未再限定 200 | 必须 200，并校验 requestId、计数和错误定位 | 必须 200，并校验 requestId、计数和错误定位 | 必须 200、eventId 一致且 status 为 accepted/duplicate |
| 408/429/5xx | 网络层标为可重试，错误体 retryable 可覆盖 | 不在永久列表，重试 | 可重试 | 可重试，最多 10 次 | 408/503 可重试，最多 10 次；Retry-After 受 1 小时上限约束 |
| 400/401/413/415/422 | 通常永久，仍受错误体 retryable 影响 | 固定永久删除 | 永久隔离 | 永久隔离 | 400/401/403/409/413/415 进入 dead-letter |
| 403 | 通常永久，仍受错误体 retryable 影响 | 当前重试 | 永久隔离 | 永久隔离 | 永久隔离 |
| 网络/解析异常 | 保留重试 | 保留原 ZIP 重试 | 保留原事件重试 | 保留原事件重试 | 保留原 report 重试并保持原 eventId |

五个上传器均使用从 30 秒增长到最多 1 小时的指数退避，服务端给出的整数重试秒数会被约束在允许范围。内存上传器默认 10 次失败后隔离事件，内存泄漏 report 上传器使用同样的内部固定边界。

Jank 的 `NetworkResult.HttpError.retryable` 不是最终决策，Uploader 使用自己的永久状态码集合。Crash 与 FPS 虽然共用批次路由，成功响应校验并不等价。服务端对照见 [协议文档](09-服务端对接与数据协议.md)。

## 文件可靠性与生命周期

五个队列复用 Crash 文件中的 `AtomicFileWriter`：临时写入、flush/sync、重命名，防止把普通半写 JSON 当成完整记录。Jank ZIP 的生成原子性归 Rhea 所有，本仓库不重写产物。

确认后文件删除通常意味着不再发送；Jank 先写 deletePending 使“服务端确认但本地删除失败”可以只重试删除。Crash/FPS 的确认删除没有同样的持久待删标志，若删除失败可能重传，应由服务端幂等处理。

队列为应用内持久重试，没有 WorkManager、系统 Job 或进程外后台服务。应用停止执行时不会继续定时发送；下次启动恢复是可靠性链路的一部分。清除应用数据会删除这些应用私有文件。

2026-09-09 的真实联调中，设备首次请求因服务端 ClickHouse 内存表未迁移收到 HTTP 500；执行迁移后恢复
HTTP 200 并落库。同一事件重放得到 `accepted=1`、`duplicate=1`，客户端删除重复事件；当次设备队列仍保留
尚未到 `nextAttemptAtMillis` 的历史重试项，不能仅凭队列总数判断本轮上传是否全部完成。

## 排查顺序

1. 确认有效 baseUrl、宿主网络权限、Debug/Release 网络策略及服务端可达性。
2. 确认正在观察的是 current 快照、正常队列、deletePending 还是 dead-letter。
3. 用 eventId 对齐入队、请求结果和本地清理日志。
4. 检查 nextAttemptAtMillis；“点击 flush 但没有请求”可能只是尚未到重试时间。
5. 核对 HTTP 与业务响应，队列项数减少不一定是服务端接受。
