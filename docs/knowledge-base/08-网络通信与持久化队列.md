# 网络通信与持久化队列

[返回导航](README.md)

## 公共网络层

`PerformanceConfig → NativeServiceConfig → NetworkConfig → NetworkClientFactory` 创建共享 OkHttp/Retrofit 和三个专用客户端。AppKeyInterceptor 添加 `X-App-Key`；网络日志可选，使用 BASIC 等级并设置敏感头脱敏，不记录请求正文。

`retryOnConnectionFailure(false)` 把重试决策留给持久化上传器。成功、HTTP 错误、网络错误、序列化错误和未知错误映射为 `NetworkResult`；协程取消重新抛出，不当成普通失败吞掉。错误体最多保留 8 KiB，日志应使用稳定 code/事件 ID 而非完整正文。

`Retry-After` 当前仅解析整数秒，不解析 HTTP 日期形式。重试仍受队列 nextAttemptAtMillis 控制，网络恢复或手动 flush 不会强制绕过它。

## 三种队列的差异

以下根目录均相对于应用 `noBackupFilesDir`。

| 项目 | Crash | Jank | FPS |
| --- | --- | --- | --- |
| 根目录 | performance-crash-reporter | performance-jank-reporter | performance-fps-reporter |
| 保存内容 | 完整事件 JSON、重试状态 | ZIP 文件名和重试/待删除状态，ZIP 由 Rhea 保存 | current.json 聚合快照、封存事件、重试状态 |
| 入队触发 | app_start 或未处理异常 | 成功/部分导出后，以及启动对账 | 当前会话恢复或 SDK close 封存 |
| 一轮上限 | 5 批 | 5 个 ZIP | 5 批 |
| 周期/启动/网络恢复 | 支持 | 支持 | 支持，仅上传封存事件 |
| 容量 | 单批限制，正常队列无字节配额 | 原始 ZIP 配额传给 Rhea | 配额只覆盖 events |
| 过期 | 7 天，转 dead-letter | TTL 由 Rhea 管理 | 配置 TTL，删除过期封存事件 |
| 永久失败 | dead-letter | 标记待删除并删除原 ZIP | dead-letter |
| 特有恢复状态 | 原子事件记录 | deletePending 与 pending ZIP 对账 | 上次 current.json 封存 |

Crash 的 dead-letter 有默认 100 文件限制；FPS 当前没有同样的 dead-letter 数量限制。不要将某一队列的容量保证套用到另外两条链路。

## 成功判定与重试

| 分类 | Crash 当前实现 | Jank 当前实现 | FPS 当前实现 |
| --- | --- | --- | --- |
| 有响应体的 2xx | 按 errors 定位处理；未校验 HTTP 必须 200 或响应总计数 | success=true 且 accepted/duplicate；未再限定 200 | 必须 200，并校验 requestId、计数和错误定位 |
| 408/429/5xx | 网络层标为可重试，错误体 retryable 可覆盖 | 不在永久列表，重试 | 可重试 |
| 400/401/413/415/422 | 通常永久，仍受错误体 retryable 影响 | 固定永久删除 | 永久隔离 |
| 403 | 通常永久，仍受错误体 retryable 影响 | 当前重试 | 永久隔离 |
| 网络/解析异常 | 保留重试 | 保留原 ZIP 重试 | 保留原事件重试 |

三个上传器均使用从 30 秒增长到最多 1 小时的指数退避，服务端给出的整数重试秒数会被约束在允许范围。attempts 饱和值不表示到达后自动停止重试。

Jank 的 `NetworkResult.HttpError.retryable` 不是最终决策，Uploader 使用自己的永久状态码集合。Crash 与 FPS 虽然共用批次路由，成功响应校验并不等价。服务端对照见 [协议文档](09-服务端对接与数据协议.md)。

## 文件可靠性与生命周期

三个队列复用 Crash 文件中的 `AtomicFileWriter`：临时写入、flush/sync、重命名，防止把普通半写 JSON 当成完整记录。Jank ZIP 的生成原子性归 Rhea 所有，本仓库不重写产物。

确认后文件删除通常意味着不再发送；Jank 先写 deletePending 使“服务端确认但本地删除失败”可以只重试删除。Crash/FPS 的确认删除没有同样的持久待删标志，若删除失败可能重传，应由服务端幂等处理。

队列为应用内持久重试，没有 WorkManager、系统 Job 或进程外后台服务。应用停止执行时不会继续定时发送；下次启动恢复是可靠性链路的一部分。清除应用数据会删除这些应用私有文件。

## 排查顺序

1. 确认有效 baseUrl、宿主网络权限、Debug/Release 网络策略及服务端可达性。
2. 确认正在观察的是 current 快照、正常队列、deletePending 还是 dead-letter。
3. 用 eventId 对齐入队、请求结果和本地清理日志。
4. 检查 nextAttemptAtMillis；“点击 flush 但没有请求”可能只是尚未到重试时间。
5. 核对 HTTP 与业务响应，队列项数减少不一定是服务端接受。
