## 当前请求

| 链路 | 方法与相对路由 | Content-Type | 版本与载荷 |
| --- | --- | --- | --- |
| Crash/启动 | POST ingest/v1/batches | application/json | X-Schema-Version 来自 service.schemaVersion，默认 2；事件信封包含 packageName |
| FPS | POST ingest/v1/batches | application/json | X-Schema-Version 固定 2；frame_scene_summary，包含 packageName |
| 内存 | POST ingest/v1/batches | application/json | X-Schema-Version 固定 2；memory_sample，包含 packageName 和 memorySample |
| Jank | POST ingest/v1/stack-artifacts:parse | application/vnd.shanshui.rheajank+zip | 原始 ZIP；manifest 版本由外部 Rhea 生成 |
| 内存泄漏报告 | POST ingest/v1/memory-reports | multipart/form-data | `metadata` 与 `report` 两个 `application/json` part；本客户端暂不上传 `hprof` |

以上请求均由公共拦截器加 `X-App-Key`。路由相对于 normalizedBaseUrl 解析，不默认剥掉 baseUrl 中的路径前缀。Crash/FPS/内存当前发送普通 JSON，内存泄漏报告使用 multipart；客户端没有添加 gzip 请求压缩。

## Crash 和 FPS 信封

共同字段包括 requestId、events，以及事件级 eventId、eventType、occurredAt、sessionId、anonymousDeviceId、版本/buildId、环境、渠道、设备信息。

Crash 还包含 `crash.throwableChain`，每层记录 type、脱敏 message 和 frames；事件工厂同时产生不含 crash 载荷的 `app_start`。

FPS 的 `frameSceneSummary` 包含：

| 字段 | 当前语义 |
| --- | --- |
| scene | 稳定业务场景或 Activity 类名 |
| algorithmVersion | fps-v1，与 schemaVersion=2 分开解释 |
| activeDurationMs | 合并纳秒有效时长向上取整为毫秒 |
| uiRefreshFrameCount | 实际采纳的有效刷新帧数 |
| refreshRateHz | 对应刷新率桶 |
| normalizedFps60 | 以原始计数与纳秒时长计算的归一化 FPS |
| frameDurationHistogram | 模型可选字段，当前 Reporter 未填充 |

批次响应有 accepted/rejected/duplicate、retryable、retryAfterSeconds、errors。errors 通过 index 或 eventId 定位事件。Crash 客户端会校验 requestId、三类计数和错误定位后再确认队列；FPS 的响应策略见 [网络与队列](08-网络通信与持久化队列.md)。

内存 `memorySample` 包含 `pssBytes`、`vssBytes`、`javaHeapUsedBytes`、`processName`、`foreground` 和可选 `scene`；三项指标允许独立缺失，但不能把读取失败写成零。客户端固定检查 HTTP 200、requestId、三类计数和事件错误定位，accepted/duplicate 才从本地队列删除。

内存泄漏报告接口要求 metadata 仅包含 `schemaVersion=1`、`eventId`、`occurredAt`、`packageName`、
`appVersion`、`versionCode`、`anonymousDeviceId`、`processName` 及可选的 `sessionId`、`buildId`、
`environment`、`channel`；report 必须保留 KOOM `hprof.json` 的 `runningInfo`、`gcPaths`、
`classInfos`、`leakObjects` 根结构。客户端把任务持久化到独立的 report 队列，成功只接受 HTTP 200
且响应 `eventId` 一致、status 为 `accepted` 或 `duplicate`；HTTP 503、超时和网络异常按原
eventId 重试，400、401、403、409、413、415 进入隔离。当前客户端不创建 `hprof` part，KOOM
生成的 HPROF 仅在本地回调中删除。

## Jank ZIP 契约

服务端要求 `schemaVersion=3`、`artifactType=RHEA_JANK`，ZIP 内为 manifest.json、sampling.bin、sampling-mapping.bin。上传原始字节，不使用 multipart、Base64 或二次封装。

manifest 包含事件身份、packageName/版本/buildId、环境/渠道/设备、scene、messageStartNs/messageEndNs、thresholdNs、minSampleIntervalNs、attemptedSampleCount、processId，以及两个二进制文件的声明大小和 SHA-256。

墙上时钟 occurredAt 与单调时钟消息区间分别使用，不相减。attemptedSampleCount 是客户端尝试计数；服务端依据解析出的主线程证据计算质量字段，不能把它当作成功采样数。

服务端要求 packageName 与 App Key 绑定包名完全匹配；不接受旧 manifest appId。mapping 由认证应用与 buildId 查找，本客户端不发送 X-Mapping-Id。公开 JankConfig.mappingId 仍会传入 Rhea，但不能据此认为服务端以该字段选择 mapping。

成功响应示例：

~~~json
{"success": true, "status": "accepted"}
~~~

重复请求返回 status=duplicate，两者按服务端契约均为 HTTP 200。网络中断或暂时失败需保留原 ZIP 与 eventId；服务端幂等键是认证应用 appId + eventId。

## 已确认的对接差异

| 编号 | 当前客户端 | 所核对服务端契约 | 影响与后续处理 |
| --- | --- | --- | --- |
| P-02 | Jank 永久状态码集合不含 403 | 403 PACKAGE_NAME_MISMATCH 不可重试 | 当前会保留并重试同一错误 ZIP；需明确修正分类 |
| P-03 | Jank 有体 2xx + accepted/duplicate 即确认 | 只定义 HTTP 200 确认 | 需补严格状态校验和测试 |
| P-05 | 实际 ZIP 由同版本可变的 Maven Local AAR 生成 | 只接受 v3 manifest | 依赖坐标相同不能证明产物版本；需用当前 AAR 的真实 ZIP 核对 |

Crash 的 schema v2、`packageName` 字段、HTTP 200 限制以及批次响应的 requestId/计数/错误定位校验已完成代码、测试和文档同步；已有本地队列不会被自动改写或删除。

## 联调验收路径

1. 对齐事件模型和请求契约，核对真实 Rhea 产物内容。
2. 准备正确包名绑定的 App Key，日志仅输出脱敏配置。
3. 用同一事件验证首次 accepted、原事件重传 duplicate、暂时失败后 ID/字节不变。
4. 验证 packageName 不匹配、非法版本、损坏 ZIP 等永久错误处理。
5. 用事件查询或存储证据确认入库，再判断本地删除是否符合预期。

内存泄漏 report 还需单独验证：检查请求只存在 `metadata`、`report` 两个 JSON part，不存在 `hprof`；
验证服务端返回 `accepted`/`duplicate` 后 report 队列删除，503/网络异常时原 eventId 和 report
内容保持不变，400/401/403/409/413/415 进入客户端 dead-letter。当前这些检查只有 JVM
MockWebServer/队列测试证据，尚无真实 KOOM 产物和服务端联调证据。

服务端文档中已有的历史验收记录属于其自身验证范围，不构成本客户端当前版本的联调结果。
