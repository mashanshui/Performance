## 启动入口

[应用 Manifest](../../app/src/main/AndroidManifest.xml) 指定 `App`，启动页是 `MainActivity`。`App.onCreate` 初始化 PerformanceSdk，打开 FPS SUMMARY 日志，随后设置主线程优先级并创建主 LooperMonitor。

应用 Manifest 声明 INTERNET 与 ACCESS_NETWORK_STATE；[Debug Manifest](../../app/src/debug/AndroidManifest.xml) 允许明文 HTTP。库自己的 Manifest 为空，接入其他宿主时应检查最终合并 Manifest，不假设宿主与示例具有相同网络策略。

**当前配置现状**：Gradle 已定义 `performance.appKey → BuildConfig.PERFORMANCE_APP_KEY`，但当前 App.kt 的初始化参数使用字符串常量，没有读取该字段。因此单独传入 Gradle 属性不会改变此调用的 Key。本文不复制原值，后续应把调用点接回配置入口；本次未修改源码。

最小接入示例见 [配置指南](../../nativelib/CONFIGURATION.md)，其中的 BuildConfig 写法是接入方式，不是当前 App.kt 的逐字描述。

## Jank 演示

1. 启动应用，检查初始化是否成功和 `isJankAvailable`。
2. 点击主页面卡顿测试按钮（资源 ID 为 button），它 post 一段大量计算到主线程。
3. 示例持有 Looper listener，每条消息开始/结束配对开启和关闭 Rhea timing；使用监控器时间区间，超过 100ms 才构造 JankEvent 并导出。MainActivity.onDestroy 注销监听并收尾未结束计时。
4. 按 eventId 依次观察请求提交、导出结果、queued、HTTP outcome 与本地删除；同时检查 ZIP
   manifest 的 `processId` 是 UUID v4、`threadScope=main`，并与采样 extra 一致。

按钮计算的真实耗时取决于设备，不保证每次产生相同区间。示例不是固定数据集，也不保证全部区间具有足够采样。ZIP 格式校验需要检查当前 Rhea 实际产物。

示例导出回调在判断成功前读取 artifact.path，失败时能否安全读取需要结合 Rhea 类型契约验证。调试代码应先分辨导出状态，不依赖无条件文件路径日志。

## FPS 演示

从主页面“FPS 测试”入口进入 `TestFPSActivity`，页面显示 400 行列表及四个操作：

| 操作 | 预期行为与观察点 |
| --- | --- |
| 开始自动滚动 | 使用 postOnAnimation 每次移动 12px，场景 fps_test_scroll；观察真实帧摘要 |
| 停止自动滚动 | 移除滚动回调并切 fps_test_idle；静止时不补造 0 FPS |
| 注入慢帧 | 切 fps_test_slow_frame，主线程阻塞一次约 120ms；结合实际 FrameMetrics 观察 |
| 恢复默认场景 | setFpsScene(null)，恢复 Activity 完整类名 |

页面 pause 会停滚动，destroy 移除回调并清理 adapter；返回页面时重置为空闲状态。

观察 `FpsHelperV2` 和 `FpsReporter` 日志。SUMMARY 每秒数值是日志区间，scene 日志是结算区间；二者与上传事件的时间范围不同。

验证上传时先制造有效刷新并切场景或退出页面，使 Helper 结算，再等待快照。下一次初始化恢复封存事件后才检查请求。`pendingFpsEventCount=0` 不能说明没有采集，它不包含当前会话聚合与 Helper 桶。

## Activity 内存泄漏演示

从主页面“内存泄漏测试”入口进入 `TestMemoryLeakActivity`：

1. 点击“正常销毁（不泄漏）”，验证普通销毁对象会在 GC 后从检测队列移除。
2. 点击“制造泄漏并销毁 Activity”，页面会把已销毁 Activity 暂存在静态强引用中，然后返回主页面。
3. 当前示例 App 为了便于烟测覆盖 `MemoryLeakConfig`，使用 1 秒首次延迟、5 秒扫描间隔、1 次重检，并关闭调试器跳过；确认泄漏后，`ActivityLeakWatcher` 在后台线程调用 `OOMMonitorInitTask.dump()`。正式默认配置仍是 2 秒首次延迟、前台 60 秒扫描和最多 10 次重检。
4. 重新进入测试页面后点击“清理泄漏引用”，释放测试强引用。KOOM 进程级 `mHasDumped` 仍限制同一进程最多实际 dump 一次。

该页面只用于受控触发 Activity 泄漏，不代表服务端联调已经通过。默认配置和快速烟测配置的差异详见 [Activity 泄漏检测与 OOM 触发](14-Activity内存泄漏检测与OOM触发.md)。

## Crash 与独立工具

主页面提供“崩溃上传测试”按钮（资源 ID 为 `crashTestButton`）。点击后由 `MainActivity.triggerCrashUploadTest` 直接抛出未捕获 `IllegalStateException`，用于验证 CrashReporter 的事件落盘和崩溃前同步上传；应用随后会按系统异常处理器退出。启动时仍会尝试入队 `app_start`。

该按钮只应在 Debug 设备上使用。点击后先观察 `CrashReporter` 日志和 `POST /ingest/v1/batches` 响应，再重启应用检查 `noBackupFilesDir/performance-crash-reporter/events`、`dead-letter` 以及队列重试状态。Crash 已同步服务端 schema v2、`packageName` 和 UUID v4 `processId` 契约，修复前记录的 HTTP 400 或 dead-letter 不能当作当前版本的联调结果；Jank 的当前协议与剩余验证边界见 [协议说明](09-服务端对接与数据协议.md)。

2026-09-13 在 Pixel 4 XL / Android 13（API 33）实测：按钮点击和 Crash 采集成功，`CrashReporter` 收到 HTTP 400 并将 Crash 记录写入 `dead-letter`；因此当前验证结论是“上传请求已发出但服务端未接收”，不是联调通过。

`CPUFreeDemo.test` 和 `GcInhibitDemo.test` 只有独立示例类，没有主页面调用链。Looper 历史和超时工具同样需要明确注册，不能通过启动应用认定它们都在运行。

## 产物与排查

应用私有目录由 Context.noBackupFilesDir 决定，五个 Reporter 子目录见 [网络与队列](08-网络通信与持久化队列.md)。Jank 原始 ZIP 位置通过 Rhea pending/export API 获取。读取设备文件时使用当前设备和实际包名确认路径，避免套用其他宿主的目录。

排查顺序：初始化状态（包括只读 `sessionId`/`processId`）→ 有效采集/导出 → 队列状态 → 重试到期时间 → HTTP 响应 → 服务端查询。SUMMARY、BASIC 网络日志和逐帧 VERBOSE 各有用途；测量性能时关闭额外诊断日志。
