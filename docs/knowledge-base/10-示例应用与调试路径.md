## 启动入口

`app` 模块的 `applicationId`、`namespace` 与源码基础包名统一为 `com.shanshui.performance`，仪器测试 APK 的默认包名为 `com.shanshui.performance.test`。包名改变后，Android 将其视为独立应用，旧包的本地数据不会自动迁移；服务端按包名或进程名查询时需使用新值。库模块维持各自的命名空间。

[应用 Manifest](../../app/src/main/AndroidManifest.xml) 指定 `App`，启动页是 `MainActivity`。`App.onCreate` 初始化 PerformanceSdk，打开 FPS SUMMARY 日志，随后设置主线程优先级并创建主 LooperMonitor。

应用 Manifest 声明 INTERNET 与 ACCESS_NETWORK_STATE；[Debug Manifest](../../app/src/debug/AndroidManifest.xml) 允许明文 HTTP。库自己的 Manifest 为空，接入其他宿主时应检查最终合并 Manifest，不假设宿主与示例具有相同网络策略。

**当前配置现状**：`App.kt` 读取 `performance.appKey → BuildConfig.PERFORMANCE_APP_KEY`，默认使用公开占位值 `local-demo-app-key`。真实值通过未跟踪 Gradle 属性或环境注入，不写入源码或命令行。
`performance.baseUrl` 非空时覆盖示例服务地址；`performance.versionName` / `performance.versionCode` 可构建升级测试包，默认仍为 `1.0` / `1`。
`performance.memoryJointTest=true` 仅在 Debug 启用内存联合验收：关闭其他上报组件，并允许 Debug 专属启动中断探针；默认关闭，Release 不启用该路径。验收工具及恢复原 APK/内存目录的方法见[构建测试](11-构建测试与本地发布.md#运行期内存峰值验证)。
`app/build.gradle.kts` 会在每次 Gradle 命令的配置阶段生成一次
`BuildConfig.PERFORMANCE_BUILD_ID`，`App.kt` 将其传入 `CrashConfig.buildId`；SDK 随后把该值复用到
Crash、Jank、FPS、内存和内存泄漏 report。buildId 格式为
`versionName-versionCode-UTC时间戳-8位随机十六进制`，对应 APK 与 R8 mapping 应一起归档。
APK 打包时会自动将相同的 buildId 导出到
`app/build/outputs/build-info/<变体名>/build-info.json`，用于发布归档和服务端 mapping 上传；
字段及触发范围见 [打包时导出 buildId](11-构建测试与本地发布.md#打包时导出-buildid)。

最小接入示例见 [配置指南](16-SDK配置指南.md)。

## Jank 演示

页面示例见 [独立卡顿测试页](images/jank-test-page.png)。

1. 首页点击“卡顿测试”进入 `TestJankActivity`，进入时不自动运行。顶部显示配置、同步/异步实际状态和 SDK 队列可用性。
2. 选择 300、1000 或 3000ms（默认 1000ms），点击“纯计算卡顿”“阻塞卡顿”或“计算并同步抓栈”。
3. 准备状态先绘制，再执行主线程负载；执行和导出期间禁用重复触发。初始化时等待就绪，无来源时可作为对照运行。
4. 结束后自动导出本次时间窗口，查看耗时、手工调用次数、导出状态、记录数、被覆盖记录数、文件大小和是否入队。
5. 使用“复制导出时 ZIP 路径”获取原路径；文件上传清理后路径可能失效。已入队不代表服务端接收成功。

示例在 [App.JANK_TEST_CONFIG](../../app/src/main/java/com/shanshui/performance/App.kt) 固定参数：

```kotlin
JankConfig(
    enableSyncSampling = false,
    enableAsyncSampling = true,
    asyncSampleIntervalMillis = 50L,
)
```

没有新增构建参数或页面模式切换。对比同步、混合和全关时，修改同一初始化对象的两项采样开关并重建安装；全关时保持 `enabled=true`，仅将两项采样开关关闭。
纯计算不调用手工抓栈；阻塞采用主线程休眠；第三种场景每约 10ms 调用一次手工抓栈，同步关闭时无效。
离页取消尚未开始的负载和重试，已受理导出继续完成。页面不注册 Looper 监听，也不停止全局采集。

导出状态必须区分成功、部分覆盖、空数据和失败。测试页不能证明精确方法耗时或上传联调成功。

## FPS 演示

从主页面“FPS 测试”入口进入 `TestFPSActivity`，页面显示 400 行列表及四个操作：

| 操作 | 预期行为与观察点 |
| --- | --- |
| 开始自动滚动 | 使用 postOnAnimation 每次移动 12px，场景 fps_test_scroll；观察真实帧摘要 |
| 停止自动滚动 | 移除滚动回调并切 fps_test_idle；静止时不补造 0 FPS |
| 注入慢帧 | 切 fps_test_slow_frame，主线程阻塞一次约 120ms；结合实际 FrameMetrics 观察 |
| 恢复默认场景 | setFpsScene(null)，恢复 Activity 完整类名 |

页面 pause 会停滚动，destroy 移除回调并清理 adapter；返回页面时重置为空闲状态。

观察 `FpsHelperV2` 和 `FpsReporter` 日志。SUMMARY 每秒数值是日志区间，scene 日志是结算区间；二者与上传事件的时间范围不同。

验证上传时先制造有效刷新并切场景或退出页面，使 Helper 结算，再等待快照。下一次初始化恢复封存事件后才检查请求。`pendingFpsEventCount=0` 不能说明没有采集，它不包含当前会话聚合与 Helper 桶。

## Activity 内存泄漏演示

从主页面“内存泄漏测试”入口进入 `TestMemoryLeakActivity`：

1. 点击“正常销毁（不泄漏）”，验证普通销毁对象会在 GC 后从检测队列移除。
2. 点击“制造泄漏并销毁 Activity”，页面会把已销毁 Activity 暂存在静态强引用中，然后返回主页面。
3. 当前示例 App 为了便于烟测覆盖 `MemoryLeakConfig`，使用 1 秒首次延迟、5 秒扫描间隔、1 次重检，并关闭调试器跳过；确认泄漏后，`ActivityLeakWatcher` 在后台线程调用 `OOMMonitorInitTask.dump()`。正式默认配置仍是 2 秒首次延迟、前台 60 秒扫描和最多 10 次重检。
4. 重新进入测试页面后点击“清理泄漏引用”，释放测试强引用。KOOM 进程级 `mHasDumped` 仍限制同一进程最多实际 dump 一次。

该页面只用于受控触发 Activity 泄漏，不代表服务端联调已经通过。默认配置和快速烟测配置的差异详见 [Activity 泄漏检测与 OOM 触发](14-Activity内存泄漏检测与OOM触发.md)。

## Crash 与独立工具

主页面统一提供“崩溃测试页面”入口（资源 ID 为 `crashCasesPageButton`），进入 `TestCrashActivity` 后点击“1. 主动抛出异常”，由 `CrashTestCases.explicitException` 抛出未捕获 `IllegalStateException`，用于验证 CrashReporter 的事件落盘和崩溃前同步上传；应用随后会按系统异常处理器退出。首页原“崩溃上传测试”按钮及独立触发方法已删除。启动时仍会尝试入队 `app_start`。

统一入口的首页截图见 [首页崩溃测试入口](images/main-crash-page-entry.png)，本次验证范围见 [构建测试](11-构建测试与本地发布.md#2026-11-04-崩溃测试入口统一)。

崩溃操作只应在受控测试设备上执行。点击后先观察 `CrashReporter` 日志和 `POST /ingest/v1/batches` 响应，再重启应用检查 `noBackupFilesDir/performance-crash-reporter/events`、`dead-letter` 以及队列重试状态。Crash 已同步服务端 schema v2、`packageName` 和 UUID v4 `processId` 契约，修复前记录的 HTTP 400 或 dead-letter 不能当作当前版本的联调结果；Jank 的当前协议与剩余验证边界见 [协议说明](09-服务端对接与数据协议.md)。

2026-09-13 在 Pixel 4 XL / Android 13（API 33）对旧版首页直接崩溃按钮实测：按钮点击和 Crash 采集成功，`CrashReporter` 收到 HTTP 400 并将 Crash 记录写入 `dead-letter`；因此当前验证结论是“上传请求已发出但服务端未接收”，不是联调通过。

`CPUFreeDemo.test` 和 `GcInhibitDemo.test` 只有独立示例类，没有主页面调用链。Looper 历史和超时工具同样需要明确注册，不能通过启动应用认定它们都在运行。

## 产物与排查

应用私有目录由 Context.noBackupFilesDir 决定，五个 Reporter 子目录见 [网络与队列](08-网络通信与持久化队列.md)。Jank 原始 ZIP 位置通过 Rhea pending/export API 获取。读取设备文件时使用当前设备和实际包名确认路径，避免套用其他宿主的目录。

排查顺序：初始化状态（包括只读 `sessionId`/`processId`）→ 有效采集/导出 → 队列状态 → 重试到期时间 → HTTP 响应 → 服务端查询。SUMMARY、BASIC 网络日志和逐帧 VERBOSE 各有用途；测量性能时关闭额外诊断日志。

## 独立崩溃测试页面（2026-10-01）

主页面点击“崩溃测试页面”进入 [TestCrashActivity](../../app/src/main/java/com/shanshui/performance/TestCrashActivity.kt)，页面可滚动，提供返回按钮。该页面统一承接原首页“崩溃上传测试”，第 1 项即可验证同一 CrashReporter 链路。该项目为测试应用，两种构建均包含此页面，不修改签名配置。

| 测试 | 操作和实际根因 | 质量验收观察点 |
|---|---|---|
| 主动抛出 | 点击第 1 项，显式抛出 IllegalStateException | 定位明确的主动测试抛出点 |
| 空指针 | 点击第 2 项，空字符串对象被强制解引用 | 定位空值与解引用 |
| 数组越界 | 点击第 3 项，长度 2 的数组访问索引 2 | 定位索引与数组长度 |
| 运行时状态 | 手工输入 expired 或 missing，点击第 4 项；ready 正常返回 | 抛出点可确定，但实际状态不在异常证据中，不能断言本次状态或上游成因 |
| 异步外部输入 | 手工输入 malformed 或 denied，点击第 5 项；accepted 正常返回 | 后台线程处理人工模拟响应，无实际网络请求；实际响应和上游任务来源未入事件 |

输入不得为空，长度最多 256 字符，去除首尾空白，禁用控件状态保存，不填写真实敏感信息。每次崩溃后重新启动应用；测试前另行记录操作、输入和时间。SDK 沿用已有采集/落盘/上传链路，联网失败时按原有队列重试。

质量验收须在固定源码提交对应的 APK 上分别触发，登记同次构建的 buildId、APK SHA-256、是否混淆及对应 mapping，再记录每例真实 eventId 和人工核验依据。不要用新的构建去登记旧 APK。后两项是证据不足候选，是否通过须检查模型实际输出是否承认缺失信息；新增按钮或单元测试通过不代表五例分析质量通过。

### 包装异常补充样本

按用户确认，页面第 6 项新增“数字解析失败（包装 cause）”：模拟计数字段 `not-a-number` 被 `toInt()` 解析，外层 IllegalStateException 的 cause 保留 NumberFormatException。无需输入或真实文件，主线程直接触发，核验模型是否沿异常链找到解析失败而非只解释外层业务错误。第 1 项显式主动异常只算闭环；第 2～6 项作为五种受控质量场景，质量结果见服务端验收记录，不能外推线上定位率。

## 2026-10-03 当前代码宿主修复样本

[CurrentCodeRepairSample.java](../../app/src/main/java/com/shanshui/performance/CurrentCodeRepairSample.java) 是本次新增的未提交受控样本，不参与 Android 界面或 SDK。parseCount 对损坏和缺失输入返回零，正常输入保留，USER_NOTE 是验收前已存在标记。它与[契约测试](../../app/src/test/java/com/shanshui/performance/CurrentCodeRepairSampleTest.java)供宿主从当前快照读取后，仅修改授权方法。既有 CrashTestCases 与主动崩溃按钮保持原意。

独立宿主从当前工作区准备分析任务，明确修复授权后提交有限补丁，实际执行三项 JVM 测试并回传修改和验证事实。另一个 runtimeState 样本因统一异常缺少实际输入与预期行为，回传证据不足并保持零写入。服务端完整证据见[当前代码验收](../../../../IdeaProjects/apm-server/docs/validation/analysis/current-code-validation.md)（依赖相邻 apm-server 外部检出）。原固定提交样本为历史验收。
