# 内存指标采集与上传


## 2026-09-22 模块化说明

当前内存指标实现归属 `performance-metrics`，Activity 泄漏 report 则归属 `performance-leak`，两条队列仍然独立。
[返回导航](README.md)

本文只描述 `MemoryConfig` / `MemoryReporter` 产生的 `memory_sample` 指标及其持久上传。
Activity 泄漏检测是另一条独立链路，使用 `MemoryLeakConfig`、`ActivityLeakWatcher` 和外部 KOOM，
不产生 `memory_sample`，不使用本页的 `MemoryEventStore` / `MemoryUploader`；详见
[Activity 内存泄漏检测与 OOM 触发](14-Activity内存泄漏检测与OOM触发.md)。

## 指标与泄漏链路分工

| 链路 | 触发与数据 | 队列/上传 | 当前边界 |
| --- | --- | --- | --- |
| 内存指标 | `MemoryReporter` 按前后台周期读取 PSS、VSS、Java heap，并复用 SDK 进程级 `sessionId`/`processId` | `MemoryEventStore` 持久化 `memory_sample`，`MemoryUploader` 发送批次 | 有历史指标设备/服务端证据；不代表泄漏检测 |
| Activity 泄漏 | `ActivityLeakWatcher` 保存 Activity 弱引用，在专用 HandlerThread 上执行 GC/finalization 和有界重检 | 达到重检次数后经 `OOMMonitorInitTask.dump()` 调用 `OOMMonitor.dumpAndAnalysis()`；分析成功后由独立 `MemoryLeakReportStore` / `MemoryLeakReportUploader` 持久上传带统一 `sessionId`/`processId` 的 report metadata，HTTP 不携带 HPROF | JVM 与 fake callback 设备测试覆盖状态机；2026-09-12 在 Huawei EML-AL00/Android API 29 以快速配置完成真实 KOOM dump、独立分析进程和 JSON 生成，未验证服务端联调 |

## 采集口径

内存 Reporter 只在主进程创建，默认启用，使用独立 `memory-sampling` 线程串行采集三项原始值。
这三项指标与 Activity 泄漏检测的判断条件和触发次数互不相等：

| 字段 | Android 读取方式 | 上传单位 |
| --- | --- | --- |
| `pssBytes` | `Debug.getPss()` 返回 KiB 后乘 `1024` | 字节 |
| `vssBytes` | `/proc/self/status` 的 `VmSize` KiB 值 | 字节 |
| `javaHeapUsedBytes` | `Runtime.totalMemory() - Runtime.freeMemory()` | 字节 |

每项读取独立容错；失败或负值写成 null，真实零值保留。三项全部缺失时不生成事件。事件同时记录
采样时间、统一的 `sessionId`/UUID v4 `processId`、完整进程名、前后台状态和前台 Activity 类名；后台不填 scene，超过 128 个字符或包含
控制字符的场景也省略。服务端字段和查询口径见外部检出仓库 `F:/IdeaProjects/apm-server/docs/api/memory-metrics-api.md`。

## 生命周期与调度

`PerformanceSdk.initialize` 在主进程完成 Reporter 注册，并从 `ActivityManager` 初始进程重要性
推断前后台状态。Activity started 计数变为非零时立即采样并切到前台周期；计数归零后等待 700 ms
确认，再立即采样并切到后台周期。旋转或页面切换恢复 Activity 时会取消旧周期，不补发错过的周期。

默认策略是前台每 60 秒、后台每 5 分钟；初始化和前后台切换都立即补采样。采样结束先写入本地
持久队列，再异步触发上传；系统没有新增保活服务、唤醒锁或精确定时闹钟。`close()` 解绑 Activity
和网络回调、取消两个调度器，已经落盘但未确认的事件留给下一次初始化恢复。

## 事件和队列

内存事件固定 `schemaVersion=2`、`eventType=memory_sample`，公共元数据复用 SDK 的应用版本、
进程级 `sessionId`/`processId`、buildId、环境、渠道、设备和匿名设备 ID。每次采样生成 UUID
`eventId`，通过临时文件、flush/sync
和重命名原子写入 `noBackupFilesDir/performance-memory-reporter/events`。

Activity 泄漏 report 不属于 `memory_sample`，不进入本页的 `MemoryEventStore`。它使用
`schemaVersion=1` 的 metadata 和独立 report 文件队列，上传到 `/ingest/v1/memory-reports`；
服务端确认 `accepted` 或 `duplicate` 后才删除本地任务，HPROF 不上传、不解析。

默认每批 20 条、512 KiB，单事件超过 256 KiB 进入 `dead-letter`；正常事件和失败隔离文件共用
20 MiB 配额，保留 7 天，超额时优先清理旧隔离文件。队列恢复、超时和网络重试都复用原 eventId
和载荷。accepted/duplicate 才删除事件，永久错误及 10 次重试耗尽的事件隔离并保留原因。

## 上传调用链

`MemoryReporter` 的 `memory-upload` 线程调用 `MemoryUploader`，通过 `NetworkClientFactory` 的
共享 OkHttp/Retrofit 发往 `POST /ingest/v1/batches`，请求头固定为 `X-Schema-Version: 2`，App Key
由公共拦截器添加。网络中断、408、429、5xx 和 503 依据 `Retry-After` 或 30 秒起步、最多 1 小时
的指数退避重试，并加入最多 1 秒随机抖动；HTTP 200 响应必须通过 requestId、accepted/duplicate/
rejected 总数和 errors 定位校验，否则保留整批。

`PerformanceSdk.isMemoryAvailable` 表示 Reporter 已创建，`pendingMemoryEventCount()` 返回正常
事件队列项数，`flush()/flushAsync()` 会请求后台上传检查但不跳过 nextAttemptAtMillis。

## 测试与边界

- `MemorySamplerTest` 覆盖 PSS KiB 转字节、VSS 解析、真实零值和独立失败。
- `MemoryUploaderTest` 覆盖 processId 字段、accepted/duplicate、稳定 eventId、异常响应保留和 503 Retry-After。
- `MemoryLeakReportNetworkClientTest`、`MemoryLeakReportStoreTest`、`MemoryLeakReportUploaderTest`
  覆盖 report-only multipart、accepted/duplicate、原子落盘、稳定 eventId、503 重试、永久错误
  隔离和过期清理。
- `MemorySamplingTimingTest` 在 Pixel 4 XL/API 33/arm64-v8a 上验证原始采集耗时；`Debug.getPss()`
  组合采集 P95 为 7.216 ms（2026-09-09 当次运行）。同一设备烟测观察到断网事件落盘、后台
  `foreground=false` 样本及重启后原 eventId/载荷保持不变。

已有的 2026-09-09 Pixel 4 XL/API 33/arm64-v8a 与本机 apm-server/ClickHouse 记录，
只针对 `memory_sample` 指标：包括 HTTP 200、`accepted=1`/`duplicate=1`、落库和 summary/trend 查询。
这些历史指标证据不能外推到 Activity 泄漏检测。2026-09-12 在 Huawei EML-AL00/API 29 使用示例
快速配置完成真实泄漏确认、KOOM dump、完整 HPROF 建索引和 Activity 泄漏路径 JSON 输出；
该结果不代表默认 10 次重检、设备 report 上传、服务端联调或跨版本兼容。断电恢复、不同 Android
版本、长时间后台功耗、事件构造与落盘细分耗时及永久拒绝/503 等设备级故障注入也仍待验证。
