# 内存指标采集与上传

## 运行期观测峰值

`performance-metrics` 仅在主进程创建 `MemoryReporter`。它继续使用 `Debug.getPss() * 1024`、
`/proc/self/status` 的 `VmSize * 1024` 和 `Runtime.totalMemory() - Runtime.freeMemory()`，
分别累计 PSS、VSS、Java 堆已使用字节的观测最大值。真实零有效；单项失败不清零，全部失败不推进有效观测截止。
每项严格创新高才替换 bytes、时间、前后台和 Activity 场景；相等保留第一次上下文。后台不借用前台 Activity。

一轮以共享 `RuntimeIdentity.processId` 为界，主进程 sessionId 与 processId 相同。同进程 SDK
close/reinitialize、Activity 重建和前后台切换都不创建新轮。采集起点是 SDK 开始采集的时刻，
lastSampledAt 是最后成功保存的有效观测时刻，不能解释为准确进程起止。墙钟回退时保持本轮时间非递减。

Activity 泄漏由 `performance-leak` 独立管理，不生成运行峰值，不使用本队列，HPROF 不随指标上传；
见[泄漏专题](14-Activity内存泄漏检测与OOM触发.md)。本次不修改泄漏、FPS、Crash 或 Jank 机制。

## current、封存与可靠替换

```text
noBackupFilesDir/performance-memory-reporter/
  current.json              本轮完整快照，不参与上传
  events/<eventId>.json      已封存原事件与独立重试状态
  dead-letter/               损坏、旧协议、冲突或永久拒绝记录
```

首个有效读数固定 UUID v4 eventId 和原身份、版本、buildId、设备及环境元数据。`MemoryPeakAccumulator`
只保留三项最大值和区间，不保存普通采样明细。新高立即写完整 current；无新高时在内存推进截止，
复用上传周期（默认 30 秒）在采样线程提交有变化的检查点，close 也尽力提交。

`MemoryAtomicFile` 写临时文件、flush、fd.sync 后保留旧备份再替换；提交前失败恢复备份，
不使用“删除旧目标后再次重命名”的回退。`.new` 不参与恢复或上传。只能保证恢复最后成功提交的版本，
突然终止或磁盘失败时尚未提交的新高、观测截止可能丢失，不依赖退出回调保证保存。

`MemoryRunRecorder.start()` 先恢复再允许采样和上传：同 processId 恢复原信封；旧 processId
先检查 TTL，再持久化同 ID events 并验证完整内容，成功后才删除旧 current，允许新轮建立。
若 events 已有相同事件，保留其 attempts/nextAttemptAtMillis；冲突事件明确隔离后重新封存有效 current。
封存失败保留唯一 current 并重试，不能凭 enqueue(false) 宣称成功。封存与上传选择共享目录锁；
旧 current 尚在时，同 ID events 不会被上传选择或配额清理。封存后再中断最多重发原 ID，由服务端去重。
损坏 current 只有隔离成功后才允许开始新轮，隔离失败不会删除原文件兜底。

默认配额 20 MiB 统计 current、events 和 dead-letter 的已提交文件字节，优先清理隔离及最旧历史，
保护唯一 current；空间不足则写入/封存失败并记录，不声称成功。替换期间临时文件和备份需要额外瞬时空间。
历史默认保留 90 天，按原 lastSampledAt 计算，恰好 90 天过期；活动 current 不被历史 TTL 清理。
封存、重试和新版本启动不会续期。旧 memory_sample 明确隔离，不推断为完整运行；不扫描其他组件目录。

## 调度、关闭和上传

采样、恢复、IO 和检查点在进程共享的 `memory-sampling` 串行线程完成，构造器不读写快照。
close 取消本实例周期并排入最终检查点；下一实例的恢复排在旧任务之后，避免旧写入覆盖新实例。
700 ms 后确认后台，初始化与状态切换立即采样，采样完成后再等待当前状态间隔，不追赶错过周期。

`memory-upload` 仅在恢复成功后读取 events。初始化、定时检查、网络恢复、手动 flush 和 close 都不会
把 current 变成历史。`pendingMemoryEventCount()` 读取后台维护的 events 文件计数，启动恢复前暂为零，
格式隔离后由后台刷新；页面读取不扫描或改写文件，也不包含尚未上传的当前轮。

上传使用 `POST /ingest/v1/batches`、`X-Schema-Version: 2`、`memory_peak_summary` / `memoryPeakSummary`，
occurredAt 等于原 lastSampledAt。完整字段以外部检出依赖的
[服务端 API](../../../../IdeaProjects/apm-server/docs/api/memory-metrics-api.md)和
[客户端接入约定](../../../../IdeaProjects/apm-server/docs/client-integration/memory-metrics.md)为准。

每批默认 20 条/512 KiB，单事件超过 256 KiB 隔离，一次 flush 最多 5 批。只有 HTTP 200、requestId
一致、计数和错误定位合法后，accepted/duplicate 才删除。网络、408/429/5xx、解析或响应一致性错误
保留原事件，遵守 Retry-After 或 30 秒至 1 小时退避（附抖动）；flush 不绕过退避。
永久拒绝或默认第 10 次失败进入隔离。关键恢复、保存、封存、确认和失败日志包含事件 ID 或文件名，不打印载荷和 App Key。

批次选择和 TTL 检查逐个读取事件，选择堆最多保留 50 个完整候选，不把整个 20 MiB 队列反序列化为常驻对象列表；
文件目录和配额元数据仍需扫描。大量旧样本隔离时只递减可见计数，避免每个文件重新全目录计数。
SDK 接管期间旧请求仍可能在途，重试提交会重新读取最新次数，不能回退已有退避或复活已确认删除的事件；达到持久次数上限直接隔离。

## 频率、测试与边界

默认前台 10 秒、后台 30 秒，依据 Pixel_6/API 35 的八段完整路径实验选择；可配置范围见
[配置指南](16-SDK配置指南.md)。完整路径测量、候选条件和结果唯一入口是
[构建测试：内存峰值](11-构建测试与本地发布.md#运行期内存峰值验证)。周期采样仍可能漏掉瞬时尖峰，模拟器证据不能推断真机功耗。

`MemoryRuntimePeaksTest` 从配套服务端唯一 fixture 检查 JSON 往返，并覆盖三项独立累计、等值、零/null、
墙钟回退、可靠替换故障、同进程恢复、跨进程封存中断、同 ID 重试保留、冲突/旧协议隔离、配额与 8/90 天边界，
以及 fake sender 两轮确认、超时后 duplicate；这些 JVM 结果不等同真实设备与服务端联合验收。
`MemorySamplingTimingTest` 另测实际完整采样路径及确定性新高/无新高检查点，`MemoryPeakFrequencyTest`
比较同负载间隔。当前执行状态及剩余联合边界见[能力状态](00-项目概览与能力状态.md)与[待验证事项](12-常见问题与待验证事项.md)。
