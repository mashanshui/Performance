# 运行期内存峰值：客户端设计

## Context

动机见 [proposal.md](proposal.md)。当前 `MemoryReporter.captureAndPersist()` 每次生成一个样本并调用 `flushAsync()`；`MemoryEventStore` 只有不可变 events/dead-letter，TTL 按入队时间；`RuntimeIdentityProvider` 在 SDK close 后仍保留同一进程身份。采样已有独立串行线程，上传另有线程，前后台默认 60 秒/5 分钟，读取与生命周期代码可复用。

共同协议、90 天边界、固定样例、执行阶段和 J1..J7 验收矩阵只维护在 [服务端 design.md](../../../../../../IdeaProjects/apm-server/openspec/changes/archive/2026-11-08-report-memory-runtime-peaks/design.md)（外部检出依赖）。本仓库只实现客户端职责，不替服务端勾选任务。与已有知识库“每次采样立即上传”的差异是本次目标，不代表已实现。

## Goals / Non-Goals

**目标：** 已持久化峰值可跨进程恢复；同进程重建不误封存；历史轮次身份和元数据不可变；写入/封存失败有可重试状态；缩短间隔有设备开销证据。

**不在范围：** 子进程合并、退出钩子保证、连续真实峰值、全部普通样本落盘、新队列框架/模块、内存泄漏/HPROF 及服务端实现。

## Decisions

### 1. 一次主进程一轮，复用现有身份

以 `RuntimeIdentity.processId` 判断本地 current 是否属于本轮；首次有效采样固定 eventId 和原元数据，collectionStartedAt 取本轮采集启动时刻。前后台切换、旋转、Activity 重建不重置；SDK close/reinitialize 若身份相同则恢复并累计同轮，不进入历史队列。close 只是停止采集，不等同于进程退出；关闭期间属于未观测区间。

主进程判断沿用既有入口，子进程不得读写同一路径。启动恢复和封存必须先于首次新采样/历史队列上传，采样线程串行编排这些状态，上传线程只能读已封存队列。

### 2. 峰值独立累计与观测截止检查点

保留 `MemorySampler` 三项独立读取及字节转换；有效零值可建立峰值，失败/缺失不清零。每项只有严格大于旧值或首次有效时更新 bytes、occurredAt、foreground、scene；相等保留首次上下文。所有采样在内存中更新 lastSampledAt，全部失败不推进有效采样时间。

出现新高立即原子写完整 current。为避免“最后采样时间”长期停留在最后一次新高，复用现有 `uploadIntervalMillis` 周期（默认 30 秒）调度到采样串行线程，对存在有效新采样的 current 保存一个检查点；它只更新完整快照，不生成普通样本或当前轮上传。无变化不反复写盘。前后台切换及正常 close 尽力提交最近有效状态，突然被杀仍只保证最后成功提交的版本。

这是在参考方案“新高及时落盘”上明确的实现补充；不新增远程字段或独立后台服务。恢复后 lastSampledAt 表示已持久化观测截止，不推断中断后的真实采样或退出时间。墙钟回退时本轮采样时间至少保持非递减，峰值时间须落在快照范围内；原事件重试不重新取时间，严重未来偏差仍按服务端错误处理。

### 3. 文件状态与可靠替换

```text
noBackupFilesDir/performance-memory-reporter/
  current.json
  events/<eventId>.json
  dead-letter/<isolated-record>.json
```

current 是一份可更新的完整快照，events 是已封存的不可变事件及独立重试状态。复用平台可靠原子文件机制或同等保证的本地实现，使写入失败仍能读取上一份完整 current；不可照搬 `AtomicFileWriter` 中“重命名失败先删除旧文件”的回退。修改共享工具只有确属本需求必要时才进行，并验证已有使用者；优先将必要处理收敛到内存快照存储。

磁盘失败不能让内存中的新高被视为已保存；保留待提交状态，在后续采样/检查点重试。日志包含 eventId、状态转换和错误类别，记录恢复、封存、确认等成功节点，避免每次普通采样高频打日志或打印 App Key/整份私有内容。

### 4. 封存先行与中断恢复

| 恢复状态 | 动作 |
|---|---|
| 无 current | 开始本轮，首个有效样本后建立 current，不生成空历史事件 |
| current 与当前 processId 相同 | 恢复原 eventId、元数据和峰值，继续采集，不封存 |
| current 属于旧 processId | 校验完整性与 TTL → 持久写 events 同 ID → 确认该文件确实存在且内容一致 → 原子替换 current 为新轮；封存失败则不覆盖旧 current，重试前不启动新轮持久化 |
| 旧 current 与同 ID events 同时存在 | 一致则视为已封存；不重复生成 ID、不覆盖既有事件或重试状态；不一致则隔离异常并记录，不能静默丢弃有效记录 |
| current 损坏 | 隔离损坏记录，保留可恢复备份，不上传半份 JSON；隔离成功后才建立新轮，隔离失败不覆盖原文件 |
| 旧轮已过期或旧 memory_sample 任务 | 有界隔离/淘汰并记录原因；不重新入队续期、不转换为运行峰值 |

当前 `enqueue()` 返回 false 只说明目标文件存在，且配额可能在入队后淘汰文件，不能直接作为可靠封存成功的依据。封存需验证完整不可变事件持久存在，并协调配额和上传，防止“队列文件已淘汰/已确认删除但旧 current 又恢复为待上传”或覆盖重试状态；可允许同一 ID 再送一次，由服务端去重，但不能丢唯一完整副本。以故障注入覆盖每个持久化边界。

临时文件/备份不作为可上传事件；清理不能删除仍是唯一有效副本的 current/封存中记录。配额包括 current、events 和 dead-letter；优先清理隔离与最旧历史，保护正在采集的 current。若空间不足以封存则保留 current 并明确记录失败，不标记成功。

### 5. 只上传历史轮次，保留原内容

初始化完成恢复、定时检查、网络恢复和 `flushAsync()` 只选择 events；当前轮采样即使创新高也不能入队。封存后使用共同 wire 模型，公共元数据来自原快照而非新运行；只允许 requestId、发送时间及本地重试状态变化，eventId、载荷、身份、峰值与 occurredAt 不变。

复用 `MemoryUploader` 每批 20 条/512 KiB、一次最多 5 批、HTTP 200/requestId/计数/错误定位验证。仅 accepted 或 duplicate 确认后删除对应历史记录；网络、408/429/5xx、解析异常及可重试事件错误保留并退避，永久错误/10 次耗尽隔离。不因 flush 绕过 nextAttemptAtMillis。TTL 默认 90 天并按 lastSampledAt 计算，sealedAt/createdAt 仅作本地调度信息，不延长有效期。

### 6. 缩短采样频率与验证门槛

保持初始化/前后台变化立即采样、串行采集、完成后再等待间隔及不追赶遗漏周期。保留公开前后台可配置间隔，具体默认值在设备实验后确定；候选为前台 5/10/30 秒、后台 30/60/120 秒，与现有 60/300 秒基线比较，不先把任何候选写成验证结论。

扩展现有 `MemorySamplingTimingTest` 测完整采集、峰值比较、原子 current 写盘和检查点路径；固定相同设备/API/ABI、构建、工作负载和持续时间，对比采样耗时 P50/P95/P99、进程 CPU、主线程调度、写盘次数/字节及合成短时上涨捕获。每个纳入选择的候选覆盖前后台至少 10 分钟并记录条件；功耗只有具备可重复测量条件时给结论，否则明确未测。

实施时根据这些证据选取可承受的更短前后台默认值，更新模块默认、服务配置常量、聚合 SDK 透传和配置文档。没有可用设备或证据不足时，该任务保持未完成，不能声称客户端全部完成；候选评估不阻塞服务端阶段 S。该实验确定参数，不改变共同 wire 契约。

### 7. 自动化与最终联调职责

纯逻辑测试使用可注入采样、身份、时钟、文件失败点和 fake sender，精确覆盖三项独立最大值、相等值、零/null、同进程重建、新进程封存、可靠替换失败、封存崩溃、配额、TTL、旧任务和确认/重试。实际进程重启、网络、升级和持久库/页面/Agent 一致性在共同 J1..J7 最后统一验证。

独立执行到 tasks 5 后可交接，tasks 6 必须等待服务端和客户端独立阶段均具备测试条件。两边任务只记录自己负责的结论和共同证据位置，不各自复制维护整套验收矩阵。

### 8. 已采用的默认频率与独立验证结论

客户端阶段 C 根据 Pixel_6/API 35/arm64-v8a 的八段各 10 分钟实验，采用前台 10 秒、后台 30 秒。完整结果、构建与中断补测条件只维护于[知识库11](../../../../docs/knowledge-base/11-构建测试与本地发布.md#运行期内存峰值验证)，不复制表格。93项JVM、4项设备独立回归及Debug/Release构建已通过；主线程心跳是顺序实验分位数，功耗、真实绘制帧因果及跨ROM未验证。用户指定Pixel6模拟器的共同J1..J7已通过，实际启动中断、升级、故障网络和三类查询入口证据仅维护于[统一验收](../../../../../../IdeaProjects/apm-server/docs/validation/memory-runtime-peaks/README.md)。两端已于2026-11-08完成核验、正式规格同步与归档，见[核验报告](verification.md)。

## Risks / Trade-offs

- [即时写盘与更短采样增加开销] → 无新高只周期检查点、不追加原始样本，设备实验测完整路径；写盘均在后台线程。
- [被杀或落盘失败丢最新更新] → 保留最后有效快照及待提交状态，不声称能恢复未持久化数据。
- [停用采集后永不再次启动] → current 不会被及时封存；文档明确该边界，不通过后台服务扩展范围。
- [SDK 同进程 close/reinitialize 的并发竞态] → 关闭/恢复与磁盘操作串行化，旧任务退出后新 Reporter 才接管，不依赖只比较 processId。
- [外部协议引用无法读取] → 在实现前恢复 apm-server 对应检出，不能凭记忆生成第二份字段表；归档时同步更新引用。

## Migration Plan

1. 等待服务端阶段 S 交接；本仓库实现并用共同样例完成 fake sender 测试，不要求先部署服务器。
2. 将旧普通内存任务按明确原因隔离，不改写为峰值；只处理此内存指标目录，保留其他功能文件。
3. 设备频率实验后更新默认配置及知识库，再进入共同阶段 J；设备实验可与联调同次安排，但不能跳过。
4. J 全部通过后分别 verify/archive，修复外部 change 引用。回滚成对构建，新峰值任务不能由旧上传器解释；不自动清除新格式数据。
