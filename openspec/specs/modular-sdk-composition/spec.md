# 模块化 SDK 组合规格

## Purpose

规定性能 SDK 全量接入与按需接入的行为边界，使消费者可以独立选择 Crash、指标、Jank 或泄漏能力，并获得一致的运行身份、生命周期与上传行为。通过可验证的缺省、失败和关闭场景，防止模块拆分引入隐式依赖或资源泄漏。

## Requirements

### Requirement: 消费者能够显式选择监控能力

SDK MUST 提供全量默认接入与显式组件装配两种方式；精简接入 MUST 不依赖全量聚合入口。运行时禁用功能 MUST 与构建时不引入功能分别定义。

#### Scenario: 仅接入 Crash

- **WHEN** 消费者只声明基础设施和 Crash 产物并注册 Crash 能力
- **THEN** 消费者能够编译、初始化和关闭 Crash，且不需要 Rhea、KOOM、ShadowHook 或自有 Native 工具的类与原生产物

#### Scenario: 仅接入指标

- **WHEN** 消费者只声明基础设施和 Metrics 产物并配置 FPS 或内存采样
- **THEN** 指标采集能够按配置启动，不要求引入 Crash、Jank、Leak、Native 工具或全量聚合产物

#### Scenario: 使用全量默认入口

- **WHEN** 消费者引入全量 SDK 并以应用实例和 App Key 初始化
- **THEN** 系统按迁移前的默认功能配置装配监控能力，且独立 Looper 监听、线程池、绑核与 GC 工具不会被隐式启动

### Requirement: 公共监控接口不泄漏采集引擎类型

SDK MUST 为初始化状态、Jank 事件、导出返回值和回调提供自身契约，消费者通过这些监控接口 MUST 不需要导入 Rhea 或 KOOM 类型。

#### Scenario: 消费者使用 Jank 导出

- **WHEN** 消费者使用 SDK 自有事件和回调调用 Jank 导出操作
- **THEN** 事件元数据被完整传递到采集引擎，导出状态和回调被映射为 SDK 自有类型

#### Scenario: 当前设备不支持 Jank

- **WHEN** 采集引擎因设备或进程条件不能启动 Jank
- **THEN** SDK 返回可区分的不支持或非主进程状态，其他符合启动条件的监控功能继续工作

### Requirement: 按需和全量接入共享身份语义

同一进程运行时的各功能 MUST 使用一致的匿名设备 ID、sessionId、processId 和共享应用元数据；身份获取 MUST 不要求启用 Crash。主进程和子进程的身份关系 MUST 保持现有服务端契约。

#### Scenario: 精简指标与全量监控使用同一身份来源

- **WHEN** 分别以精简和全量方式启动监控并读取各自同一进程内的事件
- **THEN** 每次运行内所有已启用功能共享该进程身份，设备 ID 使用既有持久化来源，Metrics 的设备 ID 不因未配置 Crash 而缺失

#### Scenario: 不同进程分别启动

- **WHEN** 主进程和子进程分别构造监控上下文
- **THEN** 主进程 sessionId 与 processId 复用同一进程实例 UUID，子进程按现有契约独立生成自身身份，不复用主进程的 processId

### Requirement: 初始化和资源释放具备明确所有权

SDK MUST 在启动前校验配置和重复功能；相同初始化请求 MUST 复用已有实例，不同配置或组件集合 MUST 报告冲突。初始化失败 MUST 清理本次已创建资源，关闭 MUST 幂等且不释放宿主或其他实例拥有的资源。

#### Scenario: 重复和冲突初始化

- **WHEN** 消费者对已初始化运行时再次提交相同配置与组件集合，或提交不同集合
- **THEN** 相同请求返回已有实例且不重复创建监听和线程；不同请求报告明确冲突且保持原实例可用

#### Scenario: 注册重复功能

- **WHEN** 同一次装配包含两个相同功能标识的组件
- **THEN** SDK 在启动任何组件之前拒绝该请求

#### Scenario: 后续组件启动失败

- **WHEN** 已有组件成功启动而后续组件在部分初始化后抛出异常
- **THEN** 失败组件清理自己的部分资源，已成功组件按逆序关闭，SDK 自建共享传输资源最后关闭，错误保留失败阶段信息

#### Scenario: 多次关闭并存在外部资源

- **WHEN** 运行时借用了外部资源或已存在的采集会话，并被连续关闭多次
- **THEN** 本次拥有的组件和共享资源最多释放一次，借用资源和外部会话不被关闭

### Requirement: 泄漏分析进程可以独立完成必要准备

已注册泄漏能力的进程 MUST 在普通采集启动判断之前完成必要的分析进程准备；分析子进程 MUST 不重复启动主进程采样与 Activity 检测。未注册泄漏能力的运行时 MUST 不加载泄漏引擎。

#### Scenario: 分析进程启动应用

- **WHEN** 全量或含 Leak 的接入方式进入 KOOM 分析子进程
- **THEN** 分析服务所需公共配置已就绪，即使 Activity 检测开关关闭也不因缺少公共配置而失败，且不重复注册主进程检测器

#### Scenario: 精简消费者启动

- **WHEN** 仅 Crash 或仅 Metrics 消费者初始化
- **THEN** 系统不会触发 KOOM 类加载、分析进程准备或泄漏回调注册

### Requirement: 拆分保持采集上传的可观察行为

各功能 MUST 保持现有默认采集口径、事件字段、认证头、端点、请求格式、持久化恢复、响应分类与重试删除语义；内存泄漏 MUST 仅上传 report JSON。模块化 MUST 不引入功能之间的自动启停关系。

#### Scenario: 恢复待上传数据

- **WHEN** 同一版本消费者重启且存在未确认上传的 Crash、Jank、FPS、Memory 或 Leak 队列项
- **THEN** 对应功能按既有规则恢复和重试，确认前不因模块迁移改变的删除规则丢失数据

#### Scenario: 按各链路处理服务端结果

- **WHEN** 服务端分别返回成功、可重试、永久失败或无效业务响应
- **THEN** 对应功能维持原有分类和队列处理结果，不用一套统一判定覆盖各链路的差异

#### Scenario: 泄漏检测与消息历史配置

- **WHEN** Activity 泄漏被确认，或消费者使用默认 Looper 配置
- **THEN** dump 仍在生命周期/UI 线程之外触发且仅排队上传 report JSON；Looper 历史及密集记录仍默认关闭、显式开启
